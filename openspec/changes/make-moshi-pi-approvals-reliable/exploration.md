# Exploration — make-moshi-pi-approvals-reliable

Phase: explore (SDD, auto mode, artifact store: openspec, delivery: ask-on-risk, review budget: 400 lines)
Date: 2026-09-13
Status: exploration only — no implementation performed.

## 1. Problem statement

A guarded-command approval made from Moshi on the phone reaches moshi-hook with the
correct `actionId`, but the daemon's TUI bridge rejects it:

```
tui bridge: pending-action.open sent   actionId=… source=pi
tui bridge: remote action executed     type=action.approve status=verification_failed
  reason="approval fingerprint no longer present on screen"
```

Measured over eight live trials: **1 sent, 7 verification_failed**. The daemon
fingerprints the pane when the `PermissionRequest` envelope arrives and re-checks
that fingerprint against the live screen when the phone's answer arrives. Something
on Pi's screen always moves in between.

Refuted hypotheses (already tested and reverted):
- Quota widget redraw (60 s `setInterval` in `extensions/quota-panel.ts`) — failed
  again after `/quota hide`.
- Envelope sent before the prompt is drawn — holding the outbound envelope 400 ms
  and 2500 ms both failed. Experiments reverted.

Non-causal but real: Herdr workspace IDs change live (w7 → w8 → w7 observed). The
stale-ID hypothesis was excluded because the daemon captured the pane before
failing; `resolveTerminalContext()` reads the env vars per extension instance, which
is correct, but any future route must not cache workspace IDs across sessions.

## 2. Exact surface map

### 2.1 Guard source — gentle-pi (installed npm package, not this repo)

`~/.pi/agent/npm/node_modules/gentle-pi/extensions/gentle-ai.ts`, `confirmCommand()`
(~lines 1568–1641):

- Classifies the bash command (`block` / `not-guarded` / `allow` / `confirm`).
- For `confirm`: `requestId = randomUUID()`, then emits on Pi's **inter-extension
  event bus**:
  `events.emit("pi-permission-system:permission-request", { requestId, state: "waiting"|"approved"|"denied", source: "tool_call", message, toolName: "bash" })`
  — `waiting` before the prompt, resolved state in a `finally`.
- The actual human gate is `await ctx.ui.confirm("Allow guarded command?", preview)`
  where `preview` is the command collapsed to one line, truncated to 180 chars.
- If `!ctx.hasUI` it blocks instead of prompting (safe fallback preserved).

### 2.2 Bridge — this repo

`extensions/moshi-approvals.ts` (piQuota):

- `pi.events.on("pi-permission-system:permission-request", …)`; validates
  `requestId` + state ∈ {waiting, approved, denied}; builds a `session.update`
  envelope (`eventName: "PermissionRequest"`, `actionId: requestId`,
  `phase: "waitingForApproval"`, `category: "approval_required"`, `toolName`,
  `message` = command preview ≤256 chars) and writes one JSON line to the daemon
  socket (`/tmp/moshi-hook.sock`, `MOSHI_SOCKET_PATH` override; named pipe on
  Windows), half-close + drain ack. `approved`/`denied` produce a
  `PermissionResolved` card.
- Terminal context resolved once per extension instance from `TMUX_*`,
  `ZELLIJ_*`, `HERDR_*` env vars (`terminalKind`, panes, workspaceId, tabId).
- Silent-failure discipline throughout (a hook must never interrupt the turn).

### 2.3 Generated extension — moshi-hook's own Pi hook

`~/.pi/agent/extensions/moshi-hooks.ts` (auto-generated by `moshi-hook install`;
must not be patched in place — regeneration would overwrite it):

- Contains `PermissionRequest` / `PermissionResolved` envelope builders for
  Claude-style hook payloads, with the comment: *"Pi owns the approval prompt and
  decision. Moshi mirrors the waiting state; with a verified terminal target the
  daemon's TUI bridge can send the user's remote decision into the native prompt."*
- Registers **no** listener on the Pi event bus — `moshi-approvals.ts` exists
  precisely to be that missing handler.

### 2.4 Daemon — closed-source Go binary

`/home/jepatino/.local/bin/moshi-hook` v0.3.21, `protocolVersion: 1`, run by the
systemd user service `~/.config/systemd/user/moshi-hook.service` (`moshi-hook serve`).
No source checkout exists on this machine; knowledge comes from `/v1/version`,
strings-level recon, and verbose daemon logs.

- Advertised capabilities: `events.watch.workspaces`, `events.watch.agent-status`,
  `events.license`, `transcripts.limit`, `terminal.prompt`, `terminal.keys`,
  `workspaces.live-se…` (truncated), `approvals.answer`.
- Local gateway routes `/v1/prompt` and `/v1/keys` are **POST-only** (GET → 405).
  Their exact request shape is unknown; they were not exercised to avoid injection.
- TUI-bridge strings observed in the binary/log: `pending-action.open sent`,
  `remote action executed`, `remote action screen capture failed`,
  `remote action has no pending interaction`, `remote action verification failed`,
  `local action executed`, `daemon: unverified permission candidate`.
- The binary contains a table of **known approval-prompt strings for other agents**:
  Claude Code (`do you want to proceed`, `press enter to confirm or esc to cancel`),
  Codex (`Choose what Codex is allowed to do`, `yes, proceed`), plus generic
  (`run this command?`, `dangerous command`, `approval required`) and
  `Answer in terminal` (the subtitle convention). gentle-pi's `Allow guarded command`
  and `gentle` appear **0 times** — Pi's prompt text is not in the daemon's table.

### 2.5 Pi platform capabilities relevant to routes

- `ui_prompt_start` / `ui_prompt_end`: notification-only lifecycle events fired
  around every blocking `ctx.ui.select/confirm/input/editor/custom` (docs/
  extensions.md §ui_prompt_start). Payload: `event.kind`, `event.title`. Handlers
  are best-effort, not awaited.
- `ctx.ui.setWorkingVisible(false)` and `ctx.ui.setWorkingIndicator({ frames: [] })`
  can hide/freeze the built-in streaming working loader from an extension.
- RPC mode has a first-class programmatic dialog protocol: `ctx.ui.confirm()` emits
  `extension_ui_request` on stdout and blocks until `extension_ui_response` arrives
  on stdin (docs/rpc.md §Extension UI Protocol). This proves Pi *can* resolve a
  dialog programmatically — but only in RPC mode, not the TUI the user runs.
- `ctx.ui.custom()` allows a fully custom TUI component in `ctx.mode === "tui"`.

## 3. Failure mechanism (working hypothesis, to be confirmed by experiment E1)

While `ctx.ui.confirm` is open, Pi's TUI is still in a "running" state and animates
— at minimum the working indicator, possibly more (status line, footer clock,
cursor). The daemon compares the pane fingerprint captured at `pending-action.open`
with a fresh capture at answer time; any moved cell invalidates it. The single
success in eight trials (12.6 s delta) suggests the check has *some* tolerance or
phase luck, not a hard timeout — failure is not monotonic in wait time
(7.6 s failed, 12.6 s passed, 33.7 s failed).

Secondary hypothesis (only if E1 shows the screen is genuinely static): the daemon
verifies by matching one of its **known prompt strings** on screen rather than a
raw hash, and Pi's prompt text is simply not in its table. The `0 occurrences` of
`Allow guarded command` in the binary makes this plausible enough to test cheaply.

## 4. Candidate routes (trust-preserving), with distinguishing evidence

Security invariants every route must keep: the phone tap is the human action and is
never synthesized; the terminal prompt stays open and authoritative as fallback; no
auto-approve; no bypass of human choice; no new exposure of secret command contents
(the envelope already mirrors a ≤256-char command preview — see Risks).

### Route A — Stable terminal prompt (fix the moving screen)

- **A1 (piQuota-local, ~20–40 lines):** on `ui_prompt_start` hide the working
  loader (`ctx.ui.setWorkingVisible(false)` / `setWorkingIndicator({frames: []})`),
  restore on `ui_prompt_end`. No daemon or gentle-pi change. The terminal prompt
  itself is untouched — this only stops Pi's own animation while *any* blocking
  prompt is open.
  - *Distinguishing evidence:* ≥10 live trials with the indicator frozen. 8/8+
    successes confirm the animation cause; continued failures point elsewhere and
    E1's diff names the remaining mover.
- **A2 (gentle-pi upstream):** render the guarded-command confirm via
  `ctx.ui.custom()` as a static overlay (no animation) while waiting.
  - *Evidence:* same trial protocol against a gentle-pi build with the static prompt.
- **A3 (fingerprint-table matching — deprioritized):** retitle the prompt to a
  string the daemon already fingerprints (e.g. Claude Code's `do you want to proceed`).
  - *Evidence for even considering it:* E1 shows a static screen yet failures
    persist → verification is known-text matching, not a hash.
  - *Why deprioritized:* fragile across daemon updates and mislabels provenance
    (Pi's prompt posing as Claude Code's). Only acceptable if the daemon's trust
    model is explicitly text-based and upstream blesses the approach.

### Route B — Daemon/gateway API integration

- **B1:** Use the daemon's own `terminal.prompt` (POST /v1/prompt) capture from the
  extension side to diff the screen at open vs answer time (this is experiment E1,
  doubles as a route: if the diff is empty, the fingerprint model itself is wrong).
- **B2:** Include a daemon-honored hint in the envelope (stable region, re-anchor
  request) — requires discovering accepted envelope fields (see D) or upstream docs.
- **B3 (upstream ask):** request a documented per-source verification policy
  (e.g. `source=pi` trusts the `actionId` match alone). The phone action remains
  the human gate; the fingerprint re-check is a staleness guard, not the consent
  mechanism — but weakening it is the daemon vendor's decision, not ours.

### Route C — Event/promise bridge (extension resolves its own prompt)

- **C1 (proof of concept only):** Pi's RPC `extension_ui_request`/`extension_ui_response`
  protocol demonstrates programmatic dialog resolution, but the user runs TUI mode.
  Not directly shippable; cited as evidence the mechanism exists.
- **C2 (cleanest end state, gentle-pi + daemon cooperation):** `confirmCommand`
  awaits **either** the terminal confirm **or** a phone answer carrying the matching
  `requestId`, delivered over a local channel. The terminal prompt stays open the
  whole time; whichever answer arrives first wins; no answer → still waiting. No
  key injection, no screen verification needed, no auto-approve.
  - *Blocked on:* the daemon has no identified approval-watch event for local
    consumers. The `events.watch.*` capability family suggests a subscription
    mechanism may exist — probing the local gateway for an approvals watch/SSE
    stream is the missing fact (experiment E4).
- **C3:** same as C2 but with the extension (not gentle-pi) subscribing to the
  gateway watch and then asking gentle-pi (via a second event-bus channel) to
  resolve the pending confirm — still needs a gentle-pi-side hook to hand over the
  pending promise, so C2 and C3 converge on a small gentle-pi change.

### Route D — Moshi hook envelope variants (local-only experiments)

- **D1:** probe envelope fields (`phase`, `category`, extra keys, alternate
  `eventName`) against a **throwaway daemon** (`MOSHI_SOCKET_PATH` override) while
  a real prompt is open, watching verbose logs for changed verification behavior.
  Never send `action.approve` synthetically; observe only.
- **D2:** use the documented debug replay path (`moshi-hook pi-hook`) to learn the
  full accepted payload schema beyond what the generated extension sends.

### Route E — Upstream modification

- **E1 = A2 + C2 in gentle-pi** (Gentleman-Programming's own package — upstreaming
  is realistic): static prompt + local answer channel.
- **E2:** file the moshi-hook issue with the 8-trial evidence, asking for (a) Pi
  prompt text in the fingerprint table, (b) region-scoped fingerprinting that
  excludes the spinner/status rows, (c) a documented local `approvals.answer`
  subscription. This is the durable fix if the daemon owns the defect.
- **E3:** Pi upstream (expose cross-extension dialog resolution or a first-class
  remote-approval API) — largest lift, not needed if C2 works.

## 5. Decisive experiments (ordered, none implement the change)

1. **E1 — screen diff:** capture the pane at `pending-action.open` and again at
   answer time during a live confirm (POST /v1/prompt if confirmed read-only; else
   terminal-native capture), and diff. Names exactly what moved — decides between
   Route A and everything else. Must confirm POST /v1/prompt is read-only first
   (ask-on-risk gate before exercising it).
2. **E2 — freeze trial:** A1 prototype, ≥10 guarded-command approvals from the
   phone. Success rate ≥ ~90% → Route A confirmed; ship A1.
3. **E3 — static-screen control:** if E2 fails while E1 shows a static screen,
   test A3's premise with one deliberately-matching title in a dev daemon only.
4. **E4 — gateway watch probe:** enumerate the local gateway's `events.watch.*`
   surface for approval-answer observability (read-only GET/subscribe attempts on
   a throwaway daemon). Decides whether C2/C3 is feasible without daemon changes.
5. **E5 — envelope schema recon:** `moshi-hook pi-hook` replay + D1 probes to map
   accepted fields (throwaway daemon; no synthetic approvals on the live daemon).

## 6. Risks

- **Closed-source daemon:** behavior may change on any moshi-hook update (v0.3.21
  today); every route keyed to binary internals (A3, D1, B2) is fragile.
- **POST /v1/prompt semantics unknown:** could be an inject-adjacent endpoint; must
  be verified read-only (or used only against a throwaway daemon) before E1 relies
  on it — this is an explicit ask-on-risk pause point.
- **Live-daemon probing can push stray cards to the phone:** all crafted-envelope
  experiments must target `MOSHI_SOCKET_PATH` throwaway daemons.
- **Small sample:** 8 trials, 1 success — not monotonic in time; conclusions about
  tolerance need ≥10 trials per variant.
- **Secret-command exposure (pre-existing):** the current envelope already sends a
  ≤256-char command preview to the phone. Any route touching the envelope should
  revisit whether that preview should be redacted on the card while keeping enough
  context for an informed approval. Parent decision, not this phase's call.
- **Herdr instability:** workspace IDs churn live; no route may cache them across
  sessions (current per-instance resolution is correct — keep it).
- **Review budget:** the likely first shippable slice (A1) is ~20–40 lines in this
  repo — far under 400. C2/E1-upstream live in the gentle-pi repo and would be a
  separate change/PR line (independent invariant, separate rollback boundary per
  RDD), so no `size:exception` is anticipated.
